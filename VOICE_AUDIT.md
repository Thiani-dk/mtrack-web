# M-Track Voice Audit

Every user-facing string in the app, extracted from source and organized to be read as a continuous script rather than by file. This is an audit only — no code was changed to produce this document.

A note on method: every string below was pulled directly from source with an exact quote and a file/function tag. Two categories turned out to matter as much as the words themselves — **strings that exist in source but are never reachable by a real user** (orphaned code paths), and **mechanics that exist but have zero copy pointing at them**. Both are flagged inline and get their own sections (4 and 5).

### Entering chat — the opening message

> "Hi! I'm M-Track. Paste in your M-PESA, Airtel Money, or bank alert messages and I'll turn them into an organised expense summary. If you use SMS Backup & Restore, you can select more than one conversation when exporting — I'll sort out what came from where."
[ChatScreen.tsx / GREETING]

This single message is doing double duty as both the greeting *and* the "paste your transactions" prompt — there is no separate instruction after it. The only other nudge toward pasting is the composer's own placeholder text, always visible, never spoken:

> "Message M-Track..."
[ChatComposer.tsx / default placeholder]

### The date-range question

**NOT CURRENTLY IMPLEMENTED.** There is no date-range question anywhere in the live app. `ChatMessage.kind` includes an `'options'` variant in the type definition, but `ChatMessageList`'s render switch has no case for it — it falls through to a generic placeholder:

> "[options] — coming in Phase 5B"
[ChatMessageList.tsx / ChatMessageItem default case]

A comment in the demo-bootstrap code confirms a date-range question was assumed to exist for real sessions: "Skip the date-range question entirely — the demo data is always the last 14 days..." [ChatScreen.tsx, comment above the demo effect] — but no code path ever sends one. A user pastes messages and the app silently scopes to whatever range the transactions happen to fall in.

### The user pastes something — a parse notice

Notices are generated by `buildParseNotices()`, one of which would fire depending on what happened to the paste. Picking the most representative example — total failure to parse:

> "Nothing came through. Those might not be transaction messages — or they got mangled on the way over. Try copying them again straight from your SMS app."
[parseNotices.ts / noParsedResult, id: 'nothing']

**Important caveat:** `buildParseNotices()` is exported but **never called anywhere in the app.** No component imports it. Every notice below exists in source but has never been shown to a real user:

> "All ${stats.parsed} transactions fall outside your date range. Want to widen it?"  [id: 'all-out-of-range']
> "Got ${stats.parsed} of ${stats.totalBlocks}. ${stats.rejected} didn't look like transactions, so I left them out."  [id: 'partial']
> "${outOfRangeCount} transaction${s} fell outside your date range, so I've set them aside."  [id: 'out-of-range']
> "Heads up: ${n} date${s} could be read two ways. I've gone day-first, Kenyan style — worth a glance."  [id: 'ambiguous']
> "A few of these I'm less sure about — they're marked so you can double-check before sending this anywhere."  [id: 'lowconf']
> "Left out ${stats.holds} authorisation hold${s} and ${stats.failed} failed payment${s} — flip them back on if you want them counted."  [id: 'holdsfailed']
> "Cleaned out ${n} duplicate${s} while I was at it."  [id: 'dupes']
[all: parseNotices.ts / buildParseNotices]

What a user actually sees instead, once parsing succeeds, is one of these three (mutually exclusive, decided by transaction count):

> "Nothing left to include — every transaction was filtered or excluded."
> "Not much to go on with ${scoped.length} transaction${s} — but here's your summary."
> "Nothing jumped out, but here's your summary." *(used when parsing succeeded but no insight cleared its threshold)*
[ChatScreen.tsx / deliverInsights]

### The insights sequence

Before insights, a lead-in is picked at random from four:

> "Here's what stood out." / "A few things I noticed." / "Worth knowing:" / "Quick read on this lot:"
[ChatScreen.tsx / LEAD_INS]

Then up to five insight bubbles stream in, one every ~400ms, sorted by internal priority (the fee insight is always kept if it exists, even bumping a lower-priority one). Full set below, in priority order (highest first) — a real session sees at most 5 of these plus a guaranteed fee_total if one applies:

> **milestone** (priority 95) — "That's your ${ordinal} summary." *or* "You've now tracked ${stats.totalTransactionsTracked} transactions with M-Track." *or* "You've now tracked ${fmtProse(projected)} with M-Track."
[insights/generators.ts / milestone]

> **fee_total** (priority 90) — "You paid ${fmtProse(total)} in M-PESA fees ${ctx.dateRangeLabel}." — detail: "At this rate that's about ${fmtProse(annual)} a year."
[insights/generators.ts / feeTotal]

> **subscription_load** (priority 88) — "You're running ${byMerchant.size} subscriptions — ${fmtProse(total)} ${ctx.dateRangeLabel}." — detail: "That's ${names.join(', ')}." (+ optionally "Roughly ${fmtProse(monthly)} a month at this pace.")
[insights/generators.ts / subscriptionLoad]

> **top_category** (priority 85) — "${topKey} took the biggest bite — ${fmtProse(topTotal)}, ${fmtPercent(pct)} of everything you spent." — detail: "Mostly ${joinNatural(topRecipients)}."
[insights/generators.ts / topCategory]

> **comparison** (priority 82) — "${biggest.category} is ${direction} ${fmtPercent(Math.abs(biggest.pctChange))} on last month."
[insights/generators.ts / comparison]

> **recurring** (priority 80) — "Found ${patterns.length} payment${s} that look regular." — detail (short batch): "Only looking at ${ctx.dayCount} days here — run a longer range to spot monthly patterns." — detail (normal): "${p.recipient}, ${p.cadence}."
[insights/generators.ts / recurring]

> **fee_trend** (priority 78) — "Your fees are running ${higher/lower} than usual this time." — detail: "${fmtProse(thisFees)} vs your usual ${fmtProse(avgMonthlyFees)}."
[insights/generators.ts / feeTrendVsHistory]

> **inflow_outflow** (priority 75) — "You came out ahead by ${fmtProse(net)}." *or* "You spent ${fmtProse(Math.abs(net))} more than came in."
[insights/generators.ts / inflowOutflow]

> **biggest_single** (priority 70) — "Your biggest single payment was ${fmtProse(biggest.amount)} to ${displayName(biggest)}."
[insights/generators.ts / biggestSingle]

> **spend_velocity** (priority 65) — "You averaged ${fmtProse(perDay)} a day." — detail: "Spending picked up in the second half." *or* "You eased off toward the end."
[insights/generators.ts / spendVelocity]

> **business_vs_personal** (priority 60) — "${fmtPercent(bizPct)}% of your spending went to businesses, ${fmtPercent(100 - bizPct)}% to people."
[insights/generators.ts / businessVsPersonal]

> **merchant_frequency** (priority 55) — "${topName} saw you ${topBucket.length} times — ${fmtProse(total)} altogether."
[insights/generators.ts / merchantFrequency]

> **busiest_day** (priority 50) — "${weekday} was your busiest — ${busiest.length} transactions, ${fmtProse(amount)}."
[insights/generators.ts / busiestDay]

> **small_spend_creep** (priority 45) — "${small.length} small payments under Ksh 200 added up to ${fmtProse(total)}." — detail: "Easy to miss individually."
[insights/generators.ts / smallSpendCreep]

Each insight bubble can carry a Share button — "Share this", which flips to "Copied" or "Shared" once used, under a fixed dialog title "Something I found with M-Track" [ChatInsight.tsx]. The shared text itself is generated separately (see § share prompt below).

Personal-record lines can also appear here, once per beaten record, only from a user's second real session onward:

> "That's your lowest fee month yet — ${fmt(a.lowestFeeMonth.amount)}."
> "Most transactions you've sorted in one go: ${a.mostTransactionsInOneSummary}."
> "Biggest single payment you've tracked: ${fmt(a.largestSingleTransaction.amount)}."
[recordMessages.ts / describeNewRecords]

### The recurring-pattern message

Separate from the "recurring" insight headline above, a richer expandable bubble appears if `detectRecurring()` found anything:

> "${patterns.length} regular payment${s}"
[ChatRecurring.tsx]

Expanding a pattern row reveals cadence chips (Weekly / Fortnightly / Monthly / Irregular), an optional "same amount each time" tag, and:

> "${pattern.occurrences.length}× · avg ${fmt(pattern.averageAmount)}" (+ optionally "· next expected around ${date}")
[ChatRecurring.tsx / PatternRow]

### The interactive receipt's section headers

The **on-screen interactive receipt** (`ChatReceiptVisual.tsx`, what a user actually sees in the chat, distinct from the downloaded file) has no printed section-header banners like the PDF does. Its structure is field labels inside a tap-to-expand row:

> "Label" / "Merchant" / "Location" / "Provider" / "Ref" / "Fee"
[ChatReceiptVisual.tsx / TransactionRow expanded detail]

...a collapsed-remainder affordance once past 12 transactions:

> "+${rest.length} more transaction${s}"
[ChatReceiptVisual.tsx]

...and the tally finale:

> "Transactions counted" / "Total transaction amount" / "Total transaction cost" / "GRAND TOTAL"
[ChatReceiptVisual.tsx / tally block]

The **downloaded PDF/HTML**, by contrast, is a full printed document with headers the interactive view never shows on screen:

> "M-TRACK" / "EXPENSE SUMMARY" / "CATEGORY SUMMARY" / "RECURRING PAYMENTS" / "TOTALS" / "FEE BREAKDOWN" / "TALLY" / "GENERATED BY M-TRACK" / "MADE WITH M-TRACK"
[receiptGenerator.ts / generateReceiptHTML, generateReceiptPDF]

Plus the compliance disclaimer, printed on every download, never shown in-chat:

> "THIS IS NOT A TAX INVOICE" / "For record-keeping only. Not valid for eTIMS or VAT claims. Obtain eTIMS invoices from your suppliers."
[receiptGenerator.ts / DISCLAIMER_LINES]

...and, on demo receipts specifically:

> "SAMPLE — NOT REAL DATA"
[receiptGenerator.ts / DEMO_LINE]

Line-item field labels inside both formats: "Items sent" / "Items received" / "Transaction fees" / "NET" / "TOTAL + FEES" [receiptGenerator.ts / TOTALS block]; fee-breakdown group names "Send Money" / "Pochi la Biashara" / "Paybill / Till" / "Withdrawal" / "Airtime" / "Other" [receiptGenerator.ts]; category fallback "Unlabelled" [receiptGenerator.ts]; recipient fallbacks for transactions with no identifiable name — "AIRTIME" / "DATA BUNDLE" / "M-SHWARI" / "ZIIDI MMF" / "CASH WITHDRAWAL" [receiptGenerator.ts / getRecipientShort], and, one layer further back in the parser itself, "Airtime" / "Data Bundle" / "Cash Withdrawal" / "Savings" [parsers/index.ts / fallbackNameForMethod] — the same four concepts, cased differently, generated by two different functions.

## 2. REPETITION MAP

Openers with two or more independent occurrences — the same rhythm or word choice reused across features that were evidently never compared against each other.

- "Found four or more active subscriptions in one summary." [badges/definitions.ts / Subscription Slayer]

- "Nothing came through. Those might not be transaction messages..." [parseNotices.ts / noParsedResult — orphaned]
- "Nothing left to include — every transaction was filtered or excluded." [ChatScreen.tsx / deliverInsights]
- "Nothing jumped out, but here's your summary." [ChatScreen.tsx / deliverInsights]

**"That's..."**
- "That's a new one." [ChatScreen.tsx / BADGE_LEAD_INS]
- "That's your lowest fee month yet — {amount}." [recordMessages.ts / describeNewRecords]
- "That's your ${ordinal} summary." [insights/generators.ts / milestone]
- "That's ${names.join(', ')}." [insights/generators.ts / subscriptionLoad, detail line]

**"You just..." / "You've..." (near-cluster)**
- "You just earned something." [ChatScreen.tsx / BADGE_LEAD_INS]
- "You've now tracked ${n} transactions with M-Track." [insights/generators.ts / milestone]
- "You've now tracked ${amount} with M-Track." [insights/generators.ts / milestone — same generator, second branch, essentially the same sentence with a different noun]

**"A few..."**
- "A few things I noticed." [ChatScreen.tsx / LEAD_INS]
- "A few of these I'm less sure about — they're marked so you can double-check..." [parseNotices.ts / lowconf — orphaned]

**"Here's..."**
- "Here's what stood out." [ChatScreen.tsx / LEAD_INS] — the only literal instance, but "here's your summary" appears mid-sentence twice more (see "Nothing..." and "Not much to go on..." entries above), meaning the word "here's" itself is doing a lot of load-bearing work across four different strings without ever being written as one shared line.

**"Tracked..." (as a badge-description opener)**
- "Tracked Ksh 1,000 in fees across all summaries." [badges/definitions.ts / Fee Auditor]
- "Tracked transactions from three or more providers." [badges/definitions.ts / Multi-Channel]
- "Tracked a single transaction over Ksh 10,000." [badges/definitions.ts / Big Ticket]

**"Sorted..."**
- "Sorted 100 transactions in total." [badges/definitions.ts / Century]
- "Sorted 500 transactions." [badges/definitions.ts / Ledger Legend]

**Same fact, two independent phrasings — not a shared opener, but worth flagging anyway:**
- "Your biggest single payment was ${amount} to ${name}." [insights/generators.ts / biggestSingle]
- "Biggest single payment you've tracked: ${amount}." [recordMessages.ts / describeNewRecords]

Two different subsystems (a per-session insight generator, and the cross-session personal-records tracker) independently arrived at describing the exact same underlying fact ("biggest single payment") in near-identical but not shared wording.

**Recurring-payment count, described twice, differently, on the same screen visit:**
- "Found ${patterns.length} payment${s} that look regular." [insights/generators.ts / recurring — the short narrative insight bubble]
- "${patterns.length} regular payment${s}" [ChatRecurring.tsx — the header of the rich expandable bubble that appears right after it]

A user sees both, back to back, describing the same number with different sentence shapes ("Found N payments that look regular" vs. "N regular payments").

## 4. INTERACTION GAPS

For each new interactive mechanic: does any copy, anywhere in the app, tell a first-time user it exists?

- **Tap-to-expand a transaction row** (in the interactive receipt) — **NOT SURFACED ANYWHERE.** No chat message, tooltip, or empty state mentions that a row can be tapped. The row itself gives no visual affordance beyond a `ChevronDown` icon that only rotates once you've already found it.

- **Tap a badge tile for evidence** (BadgesScreen) — **NOT SURFACED ANYWHERE.** Earned tiles are the only ones with an `onClick`, but nothing distinguishes an earned-and-tappable tile from an earned-but-static one visually or in copy. A locked/hidden badge does get a small hint — "Keep going." [BadgesScreen.tsx] — but that's about earning it, not about tapping an *earned* one afterward.

- **Tap GRAND TOTAL to replay its count-up** (interactive receipt) — **NOT SURFACED ANYWHERE.** No copy anywhere hints that the settled total is itself a button.

- **Tap a category bar to see its transactions** (interactive receipt) — **NOT SURFACED ANYWHERE.**

- **The label picker** (tap a row open, then tap "Add label") — **partially discoverable, but gated behind an undiscovered step.** Once a row is expanded (itself not surfaced — see above), the control is self-labeling: it literally reads "Add label" [ChatReceiptVisual.tsx]. So: discoverable via the expanded row itself, *if* the user has already found tap-to-expand on their own.

- **The repeat-share-target prompt** — discoverable via: the prompt itself, which is fully self-explanatory the moment it appears ("Add this to what you already have, or start fresh?" plus two directly-labeled buttons) [ChatScreen.tsx]. Note: the task brief describes this as "multi-select" — as built, it's a binary either/or choice between two buttons, not a multi-select control. Flagging the terminology mismatch rather than silently going along with it.

## 5. DEMO MODE COVERAGE

Demo mode runs a real parse of fake data through the exact same `deliverInsights` pipeline as a real paste, then shows the same interactive receipt component — so most mechanics are technically reachable. Whether the demo bot ever *says* to try them is a separate question.

- **Tap-to-expand a transaction row** — TECHNICALLY POSSIBLE BUT NOT CALLED OUT. The demo receipt is the same live `ChatReceiptVisual`, fully interactive, but no demo message ever says "try tapping a row."

- **Tap GRAND TOTAL to replay** — TECHNICALLY POSSIBLE BUT NOT CALLED OUT.

- **Tap a category bar** — TECHNICALLY POSSIBLE BUT NOT CALLED OUT.

- **The label picker** — TECHNICALLY POSSIBLE BUT NOT CALLED OUT. `handleLabelChange` doesn't special-case demo sessions for the labeling itself (only the badge-recheck is skipped), so labeling works identically in demo. Nothing in `DEMO_INTRO` or `DEMO_NEXT_STEP` mentions it.

- **Tap a badge tile for evidence** — NOT REACHABLE IN DEMO AT ALL. `deliverInsights` is called with `newlyEarnedBadges: []` hardcoded for the demo path, and the comment is explicit: "Demo history is fake and never persisted... there's no aggregate/badges to consult or update." [ChatScreen.tsx / demo bootstrap] A demo session can never produce a badge-unlock bubble, and the demo flow has no link into `BadgesScreen` at all.

- **The repeat-share-target prompt** — NOT REACHABLE IN DEMO AT ALL. Demo mode is entered via the HomeScreen's own "See it with sample data" link, never via the Android share-target path, and every piece of the pending-draft/share-prompt logic is explicitly gated behind `isDemoSession` checks that short-circuit before any of it runs.

## Appendix: two other orphaned pieces worth knowing about

Not asked for directly, but they surfaced during extraction and materially affect how much of this document a real user will ever actually encounter:

- **`buildParseNotices()`** [parseNotices.ts] — a fully-built, well-written set of seven notice variants (see § 1) that is never imported or called anywhere in the app. Currently the app degrades to just three coarse messages ("Nothing left to include...", "Not much to go on...", "Nothing jumped out...") for everything that would have gone through this system.

- **`getExclusionReason()` / `buildFoundSummary()`** [transactionDisplay.ts] — same situation: defined, exported, never called. `getExclusionReason` would explain *why* a transaction got auto-excluded ("Authorisation hold", "Payment declined", "Verification charge") but nothing in the current UI surfaces that reasoning per-transaction; the closest thing a user gets is the aggregate, never-fired parse notice above.

- **`ExpenseLabel`** [types/index.ts, field `ParsedTransaction.label`] — a full second labeling vocabulary (Cost of Sales, Transport & Travel, Utilities, Airtime & Data, Supplier Payment, Staff Payment, Meals & Entertainment, Medical, Rent & Accommodation, Equipment & Supplies, Investment / Savings, Personal, Other Business Expense) that predates the `receiptLabel` free-text field the current label picker actually writes to. It's still in the type, still on every parsed transaction, and never read or displayed by any current component.
